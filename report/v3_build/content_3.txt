== 7.2 Development and Test Environment
Development and testing were done entirely on a Windows 11 laptop equipped with an NVIDIA RTX 3070 Laptop GPU (CUDA 12) and Python 3.11. Language-model calls went first to Gemini and then to Groq, so the fallback chain was exercised during normal testing and not only in theory.
== 7.3 Module 1: Leaf Pathology
The classifier is a PyTorch ResNet-50 modified with a dropout layer (0.4) and a linear layer from 2048 features to 5 outputs. The saved model is approximately 94 MB. The uploaded image is converted to RGB, resized to 224 x 224, normalised and fed into the network. The result (class, confidence and full probability vector) is cached under the SHA-256 key in the cache table. Training and inference use the same preprocessing function to eliminate one common source of silent error. The procedure is given in Algorithm 7.1.
A: Algorithm 7.1: Leaf classification with caching and confidence gate
INPUT: image, user_id, language, query
1. key <- SHA256(image + user_id + language + query)
2. IF key exists in cache THEN RETURN cached result
3. tensor <- Normalise(Resize(ToRGB(image), 224 x 224))   // reject if unreadable
4. probs <- Softmax(ResNet50(tensor))
5. label <- argmax(probs); conf <- 100 * max(probs)
6. IF conf < 75 THEN mark result as "uncertain" (broader guidance)
7. store (label, conf, probs) in cache under key
8. RETURN label, conf, probs

== 7.4 Module 2: Advisory Engine
The retrieval code builds two indexes over the same CCRI passages, one from bge-m3 vectors and another from the tokenised text using BM25. The microclimate service fetches the temperature, humidity and rainfall from Open-Meteo, which are used to calculate the favourability rule. The generator first tries Gemini 2.5 Flash; if it fails or reaches its limit, it falls back to the Groq-hosted model, and finally to the offline guide and the retrieved text. An empty response from a model is treated as a failure and leads to the next fallback.
The dosage audit extracts quantities from the answer using a regular expression and checks that each quantity appears in the retrieved passages. In the first version of the pattern, the word-boundary marker (which does not match immediately after a percent sign) meant that percentage doses were missed. The boundary logic was rewritten and a regression test was added. Number words are now also converted to digits, so that "four litres" is audited as "4 L". The complete procedure is given in Algorithm 7.2.
A: Algorithm 7.2: Hybrid retrieval, generation and dosage audit
INPUT: disease, question, gps (optional)
1. weather <- OpenMeteo(gps) IF gps given ELSE none   // never fabricate
2. q <- question + disease
3. D <- top 20 of FAISS_search(bge-m3(q)); S <- top 20 of BM25_search(q)
4. FOR each passage d in D and S: score(d) <- 1/(60+rank_D) + 1/(60+rank_S)
5. C <- passages sorted by score
6. R <- top 3 of C ranked by Sigmoid(CrossEncoder(q, passage)),
      +0.1 if tag = disease, near-duplicates skipped
7. prompt <- disease + weather + R + question
8. answer <- Gemini(prompt) ON FAILURE Groq(prompt) ON FAILURE offline guide + text of R
9. IF every dosage in answer occurs in R THEN label <- "Verified" ELSE label <- "Caution"
10. RETURN answer, label

== 7.5 Module 3: Chatbot
The language router asks the language model for the language of the message and one English search question, and falls back to a short regular-expression function over Unicode character ranges. For a Kannada query, the English question is used for retrieval and an instruction to answer in Kannada script is added. Audio is resampled to 16 kHz and handed to the speech chain. The conversation history, weather and latest diagnosis are merged with the retrieved passages into the prompt. Leaf images sent in the chat are saved as sanitised files and linked to the thread through SQLAlchemy. One chatbot turn is given in Algorithm 7.3.
A: Algorithm 7.3: Chatbot turn
INPUT: text or audio, user_id, thread_id, gps, image (optional)
1. IF audio THEN text <- STT_Cascade(Resample(audio, 16 kHz))
2. (english_query, target_language) <- Router(text, last 2 exchanges)   // Unicode check as fallback
3. weather <- OpenMeteo(gps) IF gps given
4. diagnosis <- ResNet50 result IF image given ELSE latest scan of user
5. passages <- HybridRetrieve(english_query, diagnosis)
6. prompt <- last 8 turns + weather + diagnosis + passages + language rule
7. reply <- Gemini(prompt) ON FAILURE Groq(prompt) ON FAILURE offline reply
8. save turn (and image file) to thread_id; RETURN reply

== 7.6 Module 4: Marketplace
The marketplace is a FastAPI router over SQLAlchemy models. Photos are stored as sanitised files, with their captions in the database. Distance is computed in Python for each listing, and the Maps, tel: and wa.me links are generated on the server and opened through Android intents by the Capacitor wrapper. Listing creation and the nearby search are given in Algorithm 7.4.
A: Algorithm 7.4: Listing creation and nearby search
CREATE:
1. VALIDATE price > 0, quantity > 0, phone is valid   // else reject
2. qty_kg, price_per_kg <- Normalise(quantity, unit, price, price_unit)
3. photos <- up to 8 sanitised image files with captions
4. maps_url <- Maps link from farm latitude and longitude
5. save listing to database
SEARCH:
6. FOR each listing L: L.distance <- Haversine(buyer, L.location)
7. apply price, variety, distance and keyword filters
8. sort listings by distance ascending
9. attach wa.me link with URL-encoded message; RETURN listings

== 7.8 Benefits and Drawbacks of the Approach
**Benefits.** The fast backend suite runs without a GPU, using deterministic fakes for the models, so it was possible to run it after nearly every change. It discovered real bugs, such as cache-key collisions, the failure to audit percentages and the absence of a guard against an empty language-model reply (Section 8.4). It also confirmed the zero-mock weather rule and the 403 response returned when a user attempts to access another user's data, for the cases tested.
**Drawbacks.** Some tests require NVIDIA hardware, although a CPU fallback exists. The free tier of Gemini is limited to about 20 requests per day, so fallbacks to Groq and local resources were needed. The fast tests rely on synthetic leaf images rather than a large set of actual field photographs, so they do not report the accuracy of the diagnosis in the field.

== 8.2 Accuracy of the Classifier
The CNN achieved a validation accuracy of 90% and an accuracy of 80% on new leaf images. A later leak-free five-fold cross-validation on the public JMuBEN images measured an accuracy of 97.9% and a macro-F1 of 0.970. These results are compared in Figure 8.1.
F: fig8_1_accuracy.png | Figure 8.1: Classifier accuracy on the validation set, on new leaves and in leak-free cross-validation | 5.2
The results show that the model reaches a good accuracy on the validation data and generalises reasonably to unseen leaf images. The validation score shows that the model learned its training distribution. The new-leaf score is closer to what a grower will see, and the 10-point difference is likely due to features such as background or lighting that do not always transfer to a new photo. A model trained on a mix of clean and field images performs best on data similar to its training set, while a real estate includes lighting, soil splashes, partial leaves and overlapping foliage that no curated set captures. The same pattern was observed in Phase 2.
The leak-free evaluation was added because an audit of the JMuBEN dataset found that its 58,549 files come from only 861 distinct leaf patches, so a random split places a copy of almost every test image in the training set. With every copy of a patch kept on the same side of each fold, the classifier reaches an accuracy of 97.9%. The hardest pair is Phoma Blight and leaf miner, and the F1-score for Phoma Blight is 0.949. At the 75% confidence gate, the classifier answers 99.3% of the images, with an accuracy of 98.1% on those it answers. These images are close-up, evenly lit patches from a single dataset, so the figure is an upper bound for field photographs.
Per-class precision and recall on field photographs have not yet been calculated, so it cannot be claimed that one disease is recognised in the field more reliably than another. The practical answer that the system gives to the gap is the 75% confidence gate: when the model is unsure, the advice becomes broader and the model does not claim to be specific. The prudent course is therefore to gather more field photos, keep the gate in place and present the results as a decision aid to be verified with an agronomist.

== 8.4 Deviations and What Was Learned
Several results differed from the plan, and most of these deviations were found by the automated tests or the benchmarks. Each is described below together with the action taken.
=== 8.4.1 CNN Cold Start
The first CNN call after start-up took 704 ms against a target of 100 ms, because it includes the initialisation of CUDA. Later calls take a median of 5.3 ms on the GPU. The target was missed, and a warm-up call at start-up is planned (Section 9.8).
=== 8.4.2 Cache-Key Collisions
An early version of the result cache built its key from too few inputs. A test showed that two different questions about the same image returned the same cached answer. The language and the query were added to the key, and the test now guards against the regression.
=== 8.4.3 Percentages Missed by the Dosage Audit
The first audit pattern used a word-boundary marker that does not match immediately after a percent sign, so percentage doses such as 1% were never checked. The boundary logic was rewritten and a regression test was added. A later benchmark showed that doses written in words, such as "four litres", were also missed; number words are now converted to digits before the check.
=== 8.4.4 Empty Language-Model Replies
Gemini 2.5 Flash sometimes spent its output budget on internal "thinking" tokens and returned an advisory cut short at about 100 characters. Thinking was turned off and the output budget was raised. An empty reply, or a reply that stops at the token limit, is now treated as a failure that moves the request to Groq.
=== 8.4.5 Language-Model Quota
The free Gemini tier allows about 20 requests per day, and the quota ran out during testing. The Groq fallback and the offline guide kept every test passing, which confirmed that the fallback chain works in practice and not only on paper.
=== 8.4.6 Chatbot Faults Found by the Benchmark
The chatbot benchmark exposed three faults. The language router saw only the current message, so two of ten follow-up questions were answered wrongly; weather keywords matched inside two Kannada compound words; and the offline reply for Kannada users quoted English excerpts. The router now receives the last two exchanges, weather keywords must start a word, and the offline Kannada reply cites the document pages in Kannada. Regression tests were added for all three fixes.
== 8.5 Field Feedback
An initial round of field testing was carried out with coffee planters who were willing to try the application and give their honest feedback. Their comments on usability were positive. The round was informal: no task-completion or time-on-task figures were recorded, and the number of participants was small. A structured pilot with more growers and buyers is planned (Section 9.8).

== 8.7 Limitations
The following limitations have been identified and are acknowledged throughout the report.
# **Synthetic test data:** The fast automated tests use synthetic and deliberately corrupted images; only the four real-model tests use real sample photographs.
# **Classifier generalisation:** A gap between 90% on validation and 80% on new leaves was observed, indicating that field performance is lower than laboratory performance, and the leak-free 97.9% was measured on close-up patches from one dataset. The softmax confidence is not calibrated, and the 75% gate is a tunable value rather than a statistically derived one.
# **Dosage audit scope:** The audit verifies that a quantity appears in the retrieved text. It does not check whether the amount suits the context, and it cannot prevent a mistake in the source text.
# **No separate grading of Kannada quality:** The 12.4% word error rate is a published figure for the model. The Kannada text generated by the language model has not yet been formally reviewed by native speakers, and there is no measure of speech accuracy on farmers' recordings.
# **External service dependence:** Hosted language models are used for the advisory. The free Gemini tier allows only about 20 requests per day, so the Groq and offline fallbacks are crucial, and service changes or pricing may affect the system.
# **Grid-level weather:** Open-Meteo provides weather at grid level. The rule is therefore coarse, because it does not reflect the microclimate of a specific slope, shade level or stream.
# **Restricted range of conditions and inputs:** The classifier covers five leaf conditions. Soil data is not used in the current build, and severity is not assessed.
# **Small field trial:** Only an initial round with coffee planters has been carried out, and structured usability metrics have not yet been collected.
# **No transactions:** The marketplace connects growers and buyers but does not handle contract negotiation or payment.
# **Server dependence:** Diagnosis requires access to the backend, so growers in valleys without adequate coverage cannot use it until offline support is added.
# **Hardware-dependent performance:** Latency figures were measured on one laptop with an NVIDIA GPU and are therefore indicative.
# **Benchmarks written by the team:** The retrieval and chatbot questions were written from the knowledge-base documents and scored by a language model, so a question set collected from growers is still needed.

The system passes all of its automated tests and degrades gracefully when external services fail. == 9.3 Key Takeaways
**Grounding plus checking is safer than grounding alone.** Retrieval keeps the language model close to the source, and the dosage audit provides a low-cost check on one of the most serious types of error: the wrong quantity. This does not guarantee that the advice is safe, but it makes the advice more credible and invites closer scrutiny than an unchecked response.
**Language support is a design problem, not a translation add-on.** By detecting the language, searching in English and writing the answer in Kannada, a separate translation step was removed and the Kannada path became part of the product. Adopting a local speech model also played an important role, because it reduced the reliance on connectivity and quotas.
**Tests change what is built.** Several of the most useful improvements of this phase, from the cache key to the percent-sign fix to the empty-reply guard, were found by tests written to prove something else. A fast suite meant that it was run constantly, and it allowed four modules to be integrated without the fear that usually comes with integration.
== 9.4 What Remains Uncertain
The classifier is weaker on unseen field photographs than on its validation set, and the automated tests do not use real field images. The Kannada pipeline relies on published speech accuracy and has not been reviewed by native speakers. The advisory has been tested automatically and benchmarked, but it has not been re-evaluated by an agronomist since Phase 2. The field feedback, while positive, comes from an initial and informal round. These are the key areas to be prioritised for improvement.

== 9.6 Reasons for These Upgrades
**Offline first.** Most coffee plantations are scattered across valleys, so the biggest real-world obstacle is the need for a network connection, which a model running on the phone removes. A conflict-free replicated data type (CRDT) approach lets the phone and the server merge edits made offline, so that neither side's changes are lost, and converting the model to INT8 reduces its size considerably.
**Graph-based reasoning.** A grower's real questions often carry several restrictions, for instance which fungicide can be used on a specific cultivar during blossom showers near a stream. Answering them requires connections between a disease, its control and the restrictions on that control, which a knowledge graph represents directly and flat passage retrieval handles less reliably.
**Leaf wetness: measured, not modelled.** The length of time that leaves stay wet is an important factor in the development of rust and is not easily estimated from regional weather. On-farm sensors would allow the favourability score to be computed for the estate rather than for the nearest weather grid cell.
**Closing the sale.** At present the marketplace reaches only the point of contacting the grower. Integration with the Open Network for Digital Commerce, with escrow payments held until delivery and moisture inspection, would enable a grower to trade within the app and reach buyers outside the district.

PlantIQ takes a grower from a sick leaf to an informed treatment decision, which should always be confirmed with an agronomist, and on to a direct sale, in the grower's own language. The project's usefulness is derived from the combined contribution of all these components rather than from any single component individually.

= APPENDIX B | USER MANUAL
The following step-by-step walkthrough was used for the demonstration. It assumes a mobile phone with an internet connection, or a web browser for the web version.
== B.1 Sign In or Register
Open the app and use the Sign In / Register screen. New users tap Register and create an account with a username (or email) and a password, while returning users sign in with the same username and password. An account keeps scans, chats and listings together and private from other users.
== B.2 Scan a Leaf
Take a clear picture of the affected leaf, preferably in natural light against a plain background, with the leaf filling most of the frame. The app returns the most plausible condition and a confidence value. If the confidence is below 75%, the app does not name a single disease and provides more general guidance; in that case, take the picture again or consult an agronomist.
== B.3 Get Advice
The advice screen shows the diagnosis and the current weather at the user's location; allow access to the location if the weather should be taken into account. The advice is drawn from the CCRI text. If every chemical dose in the advice is found in the source text, the advisory is marked as verified; if any dose is not found, a caution is shown with the unverified quantities. Treat the caution as a reminder to read the product label and consult an expert before spraying.
== B.4 Ask in Kannada
When opening the chat, make sure that the leaf the assistant should know about is shown on the scan screen. Type in Kannada, English or a combination of both, or use the microphone. If the question is written in Kannada script, the reply is returned in Kannada. The assistant remembers the last 8 messages.
== B.5 List and Sell
To sell a lot, prepare a listing that includes the coffee variety, the quantity, the price per kilogram and a contact number, along with captioned photos. Listings are sorted by distance, filtered by price and searched by keyword. Buyers can open directions to the farm in Maps, call the grower or start a WhatsApp chat with a pre-written message.
